# 大型环境资源读取优化

本阶段修复环境“2”发布后拖慢全站的问题，不改声场格式、传播结果或采样精度，不放宽当前 200,000 网格单元预算。原始环境和历史运行不删除、不覆盖。

## 原因与规模

该环境有 20 个发送深度、20 个接收深度和 500 个距离点，共 200,000 个网格单元。原始到达文件约 1.4 GiB，运行声场 280,428,605 字节，声线文件 41,086,298 字节。

原实现每次读取目录、单个环境输入或声学图都同步启动 C++ 全目录适配器。适配器先在 List 中完整读取各资产，随后 Find 再次读取；前端又为目录中每个环境请求输入快照。大声场因此被反复解析，且同步调用阻塞后端事件循环。

发布和构建阶段另有整文件 read_bytes 后求 SHA256 的内存开销。文件大小是放大因素，重复读取和请求阻塞才是这次全站卡顿的直接原因。

## 本轮实施

1. 每个后端应用持有自己的已校验目录摘要。启动时仍由 C++ 完整加载；请求只检查文件身份、大小、mtime 和 ctime。目录增删或文件变化后，重新校验整个快照，再原子替换。指纹仅用于失效判断，不替代内容校验。
2. 同一应用只有一个目录刷新或正式资源检查在执行。失败指纹不会被每个浏览器请求重复重试；文件修复变化后重新检查。资源损坏返回明确错误，不继续提供旧摘要或默认环境。
3. 运行和重新运行前调用 C++ 的单环境检查入口，完整校验被选环境；Worker 仍按冻结 ID、版本和校验值装配。浏览缓存不成为运行数据源。
4. 发布和目录校验移至后台线程；与运行前资源检查共用并发锁。发布后完成目录校验才返回可运行。重复发布请求明确提示等待，不并行复制大文件。SHA256 按 1 MiB 块读取。
5. 环境目录一次读取批量名称、坐标、月份、水深摘要，不请求每个环境的完整输入。实验工作台仅为当前选择的环境加载输入快照。原环境列表 DTO 保持兼容。

核心文件：`resource_index.py`、`resources.py`、`api.py`、`authoring.py`、`resource_catalog_adapter.cpp`；前端为环境目录和实验环境选择的数据查询适配，没有重新设计页面。

## 性能验收

本机真实仓库含 7 个环境，包括未修改的环境“2”。下表为 HTTP 实测，不包含后端启动时的首次全量校验，不代表其他硬件上的保证值。

| 请求 | 原实现 | 优化后 |
| --- | ---: | ---: |
| 环境列表 | 10.815 s | 0.006–0.015 s |
| 与目录并发的系统信息 | 10.715 s | 0.0044 s |
| 与目录并发的运行列表 | 10.615 s | 0.0046 s |
| 全部环境名称与地理摘要 | 原为逐环境请求 | 0.0075 s，1080 字节 |
| 环境“2”输入快照 | 会触发全目录加载 | 0.0037 s |

真实浏览器验收：目录 1 次批量摘要、0 次完整输入请求；实验工作台未选择环境时 0 次输入请求，选择“2”后仅请求该环境 1 次。用户环境草稿前后完全一致。

读取该环境 41 MB 声线产物的请求耗时 1.161 s，返回绘图数据约 982 KB；同时请求系统信息和运行列表分别为 0.055 s、0.103 s，未等待绘图完成。声线解析仍有 CPU 成本，本轮没有把它称为零成本读取。

验收脚本：`frontend/scripts/verify-environment-catalog.mjs`。截图：

- `/tmp/environment-resource-performance-evidence/environment-catalog.png`
- `/tmp/environment-resource-performance-evidence/experiment-selected-environment.png`

回归通过：前端 261 项及生产构建、后端相关门禁 134 项、C++ ON 11 项和 OFF 5 项 smoke；OFF 适配器另通过 22 项 Python 目录与缓存契约测试，git diff --check 通过。新增覆盖缓存并发与失效、损坏后不回退、运行前独立校验、发布期间其他接口可用和重复点击拦截。真实目录路径走通发布后立即可见、模式 A/B 通信和融合业务四种运行，并拒绝损坏声场启动。

## 保留的成本与下一步

首次启动和目录发生变化后的完整校验仍与资产总量相关；运行前校验及 Worker 加载也仍需读取选定文件。单应用锁不是多进程的跨进程锁；当前部署继续采用单个后端进程。大规模并发发布需要另立任务队列与跨进程协调，不能直接增加服务进程后声称已有隔离。

20 万是当前服务预算，不是根据 175 m 水深推导的采样上限。网格数为频率数、发送深度数、接收深度数和距离数的乘积；本建设器当前只有一个频率。每个单元还包含数量不同的多径，所以点数相同也可能产生很不一样的文件大小。

下一步先补实际字节数、路径数量、构建耗时和内存峰值统计，再按测量结果评估分块存储、单环境增量索引及按需读取。只有同时通过构建、发布、运行加载和浏览器测试后再考虑提高预算。本轮不承诺取消上限，也不以丢弃物理路径换速度。

部署要求：后端和新增单环境命令的 C++ 适配器须同步更新；旧适配器遇到新命令会明确失败，不自动跳过校验。优化版验证服务为前端 4181、后端 8011；旧服务保留，历史内存运行记录不会自动迁移。
