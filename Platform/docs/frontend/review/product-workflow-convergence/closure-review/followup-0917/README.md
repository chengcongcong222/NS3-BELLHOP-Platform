## 真正的失败原因

原 Backend 已把运行记为 Failed，原因是 `TDMA slot cannot contain maximum packet airtime and guard`，不是后端离线。

当前配置：模式 B，60 bit/s，时隙 4 s，保护时间 2 s。当前最大特征帧为 15 字节，加波形校验 4 字节，共 152 bit。发送至少需要 2.533333334 s，加保护时间后至少 **4.533333334 s**。这只是发送/保护约束，并不保证所有多径链路都可解码。

原前端把 Failed 后事件流正常结束也显示成“后端连接不可用”，覆盖了真正的问题。本批修复：

- Run 状态和失败原因只来自 Run API。
- SSE 增加无业务序号的 `stream-end` 结束帧，客户端核对最后序号后关闭；丢事件不视为完整结束。
- 断线显示为可重连的观测状态，不代表仿真失败，也不替换已知的 Failed。
- 没有擅自修改“测试0917”的时隙、噪声或任何其他配置。原配置的波形噪声谱密度为 500；即使时隙改为合法值，噪声导致的解码失败仍是另一项真实实验结果，不能用前端“修好”。

## 轨迹复用

新绑定默认采用“路径跟随节点起点”。同一轨迹资源/路径可绑定多个节点，节点 X/Y/深度可以独立输入或拖动。

正式链路：源轨迹精确 ID/version/checksum → 场景起点平移完整路径 → 内容寻址、不可变的布设轨迹 → 冻结 Run Definition → C++ BoundTrajectories。

源轨迹不会改写；时间、速度、姿态不改变；无时间伸缩、尾点延长、Runtime 坐标变换或动力学求解。生成的布设轨迹保留源校验值和布设起点，可追溯，但不把每个内部实例塞进用户轨迹目录。

旧绑定继续使用原绝对坐标；用户主动选择“改为跟随场景起点”才改变方式。后端能力接口明确支持后前端才允许保存相对绑定，避免旧服务忽略字段。
